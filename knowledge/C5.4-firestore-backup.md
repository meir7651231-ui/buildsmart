# C5.4 — Firestore backup + point-in-time restore (owner-run infra)

The catalog-to-server migration puts the catalog, specs, recipes, stores and
inventory in Firestore. Before the go-live flip, set up managed backups so a bad
seed / write can be rolled back to a known-good moment. This is a **console/CLI
config the owner runs** (needs Firebase/GCP access) — there is no app code for it.

## A — Scheduled backups (recommended, managed)

Firestore Managed Backups keep daily snapshots with a retention window; PITR lets you
restore to any minute in the last 7 days.

```bash
# one-time: enable Point-In-Time Recovery (7-day window) on the (default) database
gcloud firestore databases update --database='(default)' \
  --enable-pitr --project buildsmart-b0b78

# one-time: a daily backup schedule, kept 14 days
gcloud firestore backups schedules create \
  --database='(default)' --recurrence=daily --retention=14d \
  --project buildsmart-b0b78

# list backups / schedules
gcloud firestore backups list --project buildsmart-b0b78
gcloud firestore backups schedules list --database='(default)' --project buildsmart-b0b78
```

### Restore (if a seed goes wrong)
```bash
# from a managed backup → a NEW database (review, then swap):
gcloud firestore databases restore \
  --source-backup=<BACKUP_RESOURCE> \
  --destination-database='restored-check' --project buildsmart-b0b78

# OR point-in-time clone to a new database:
gcloud firestore databases clone \
  --source-database='(default)' \
  --snapshot-time=<RFC3339-timestamp> \
  --destination-database='pitr-check' --project buildsmart-b0b78
```

## B — Manual export/import (extra belt-and-suspenders before the first seed)

```bash
# export the whole DB to a GCS bucket right BEFORE the first seed
gcloud firestore export gs://buildsmart-b0b78-backups/pre-seed-$(date +%F) \
  --project buildsmart-b0b78

# import it back if needed
gcloud firestore import gs://buildsmart-b0b78-backups/pre-seed-YYYY-MM-DD \
  --project buildsmart-b0b78
```

## Why this is safe to do before go-live
The seed collections aren't READ by the app until `useServerCatalog` flips on
(still OFF), so a backup/restore cycle here never affects users. Do a manual export
(B) immediately before the first `scripts/seed` run, so the pre-seed state is
one command away.
