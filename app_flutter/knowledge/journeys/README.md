# knowledge/journeys — the movement between screens, opened

> DECOMP-DEPTH phase N output. Auto-generated by the **read-only** journey
> decomposer (`tools/atom/decompose --journeys <file>` /
> `--journeys-batch <dir> --out app_flutter/knowledge/journeys`). Do not
> hand-edit — re-run the tool.

Where `knowledge/logic|data|primitives/` open what the app *is*, this opens what
the user *does*: the graph of screen-to-screen movement. BuildSmart routes with
**Navigator 1.0 imperative** — `MaterialApp.home = OnboardingGate`, no router, no
named table; every transition is an un-named `MaterialPageRoute` pushed by the
convention `static Route route([params])`, back is `Navigator.pop(ctx, value)`.
So the graph is **invisible to any route-table tool** — it is recovered from the
pushes.

- **[GRAPH.md](GRAPH.md)** — the whole graph: **905 nodes · 200 edges**
  (140 push · 45 provider-swap · 15 raw-push · 1 dormant), 67 route-addressable.
- per-screen dirs (`suppliers_screen/`, `home_shell/`, `store_screen/`, …) — the
  node + edge table for one screen.

## Edge kinds

| kind | meaning |
|---|---|
| `push` | `Navigator.push(ctx, Target.route(...))` — the convention. |
| `raw-push` | `Navigator.push(ctx, MaterialPageRoute(builder: …=>T()))`, **no** `route()` — an off-convention screen (Install/Audit/Camera), route-tool blind (step 78 gap). |
| `pop-return` | the screen pops a **value** up (scanner/dialogs hand a result to their caller). |
| `provider-swap` | a **Navigator-invisible** hop through a bypass surface. |

## The 3 bypass surfaces (step 73) — central arcs, no routes

These carry the busiest journeys yet no route tool can see them:

1. **`HomeShell` — tabs.** `IndexedStack` + `mainTabProvider` (4 tabs). Tab
   changes are `mainTabProvider = i`, not pushes.
2. **`store-section`.** `storeSectionProvider` (`enum StoreSection {all, cart,
   orders, services}`) swaps the Store body in place.
3. **`_OpeningFlow` — startup.** `startupStepProvider` + `PopScope` drive the
   first-run steps.

## The golden journey — browse → order (and its seam)

`Suppliers → Brand → Section → Products` is a contiguous **push chain**. Then the
order completes on a **different subtree**: add-to-cart is a *data* write
(`smartCartProvider`), and the cart/orders come forward via **provider-swaps on
the global `CartFab`** — `CartFab → Store/cart` **and** `→ HomeShell#tab3`. So
`Store/cart` is **not push-reachable** from the product screen: the browse→order
journey is *stitched by provider-swaps on a global FAB*, not one push chain. The
graph shows that seam rather than inventing a missing edge.

## The gaps (step 78) — documented, not fixed (owner-decisions)

- **No route-registry** — every screen is grepped, not tabled.
- **`IntelRouteObserver` is dead** — un-named routes never fire a `screen-view`
  for pushes.
- **Route-less screens** — `InstallStudio` / `Audit` / `Camera` are raw-pushed.
- **Dormant edges** — flag-gated transitions (e.g. `→ StockScreen` behind
  `featureOn(orgConfig, 'site', 'stock')`) are default-OFF, marked `dormant`.

**Guards:** read-only · zero app-code change · the graph is documented and its
gaps flagged; the tool never adds a router or rewires a push.
